## Phase A — Attribute Display Metadata (~2h)

**Edge-audit 2026-06-01: 14 modifications applied (3 BLOCKERS + 5 HIGH + 5 MEDIUM all addressed).**

### Schema additions

**Attribute level:**
```ts
display_type: "swatch" | "button" | "dropdown"   // default: "button"
tracks_weight: Boolean                             // default: false (owner-confirmed label)
```

**Per attribute value level:**
```ts
attribute_value_code: String                       // existing, used for hex when swatch
weight_grams_value: Number                         // optional; only meaningful when parent attribute.tracks_weight === true
```

### Admin UX

**Attribute create/edit form:**
- "Display Style" dropdown: Swatch / Button / Dropdown
- "Enable weight tracking for variations" checkbox + Bangla label
- **MOD #7: NO live preview chip in Phase A** — text hint only ("Swatch = color circles, Button = pill chips, Dropdown = native select with search"). Live preview deferred to Phase C (after PDP components built — reuse them).
- **MOD #5: Warning if 2+ axes both have tracks_weight=true** (Save still allowed; toast: "Multiple weight axes — variation weight will be SUM of all flagged values").
- **MOD #8: Update form only — warning if attribute is used in N products** ("⚠️ This attribute is used by N products. Changing display_type / tracks_weight may affect their PDP rendering and matrix weight."). Soft warning, save still allowed.
- **MOD #12: Hint near tracks_weight checkbox** — "Weight tracking auto-fills the variation matrix only when this attribute is a variation axis on a product. For spec-only attributes, weight values are informational."

**Per attribute value row:**
- Hex color picker — visible only when display_type = "swatch"
- Weight (grams) input — visible only when tracks_weight = true
- Plain text name input always

**Attribute list table:** badge column for display_type.

### Variation matrix auto-fill rules (locked)

- **MOD #4: Multi-axis sum** — variation weight = sum of `weight_grams_value` across every `tracks_weight=true` axis in this row's combination
- **MOD #13: New rows only** — auto-fill applies ONLY to rows without `_id` (freshly-generated combinations). Existing variation rows preserve their `variation_weight_grams` even if `tracks_weight` flips later. Matches the immutability pattern.
- **MOD #2: Single source of truth** — both matrix Weight column AND post-save `VariationWeightEditor` write to `variation_weight_grams`. Matrix sets initial value during create; VariationWeightEditor is for post-publish overrides + legacy products. Documented as the intentional pattern, NOT a duplicate.
- **MOD #6: Tooltip on Weight column** — "Auto-filled from {Attribute Name}'s weight value. Edit per row if needed (e.g. add packaging)."

### Backend sanitize / insertMany safety

- **MOD #3: Pre-insertMany guard** in postProduct + updateProduct — `if (v.variation_weight_grams === "") v.variation_weight_grams = null` BEFORE the `insertMany({ ordered: true })` call. Otherwise empty string casts to NaN → entire batch rolls back.
- Frontend matrix input also coerces empty → null before submit (belt + suspenders).
- attribute sanitize helper preserves new fields (`display_type`, `tracks_weight`, `weight_grams_value`) — doesn't strip them.
- weight_grams_value validation: if `tracks_weight=true`, accept positive Number or null; reject negative.

### Migration (smart-default + race-safe)

- **MOD #1: Smart-default `display_type`** — if any `attribute_values[].attribute_value_code` looks like a hex code (`/^#?[A-Fa-f0-9]{3,8}$/`) → `display_type: "swatch"`. Else → `"button"`. Avoids regressing live color attributes between Phase A ship and Phase C ship.
- All migrated attributes get `tracks_weight: false`.
- All values get `weight_grams_value: null`.
- **MOD #9: Race-safe pattern** — use `findOneAndUpdate({ _id, display_type: { $exists: false } }, ...)` so admin's mid-migration manual flip is never stomped. Idempotent — re-run is no-op.
- **MOD #10: Log breakdown** — "Found N attributes — migrated X swatch + Y button + Z skipped (already migrated)". Don't log bare count.

### Cross-phase interaction

- **MOD #14: Hardcoded "button" v1** — per-client default configurable in settings → Phase F backlog. Don't build now.
- **MOD #11: Swatch values without hex** — toast warning on save ("X values have no color code — render as empty grey circles on PDP"). Save NOT blocked. Hex data preserved across display_type flips so admin can revert without re-entering.
- Phase B filter sidebar reads `display_type` live (no cache); Phase A doesn't need to emit cache-bust signal.

### Rendering rules (PDP — Phase C implements, documented here so Phase C has the spec)

| Type | Desktop | Mobile |
|------|---------|--------|
| **Swatch** | flex-wrap up to 16, beyond → `[+N আরো]` chip → modal | flex-wrap up to 8, beyond → modal |
| **Button** | Same as swatch | Same as swatch |
| **Dropdown** | Native select with **search bar** (typeahead filter), long lists scroll inside | Same |

**Modal behavior:** search bar at top, full value list with current selection highlighted, tap-select closes modal.

**Swatch fallbacks (no hex):** empty grey circle with name beside.

**Display type override:** Color attribute with display_type=button → hex ignored, plain button rendered (admin's intentional choice, no auto-correction).

## Phase B — Category Default Attributes (~2h)

**Edge-audit 2026-06-01: 8 modifications applied (3 BLOCKERS + 4 HIGH + 1 MEDIUM all addressed).**

### Architecture: Pattern 1 — Hierarchical inheritance (Daraz/Amazon style)
- Sufficient for owner's scale (single-shop resale model)
- Attribute Groups (Pattern 2 / Magento style) deferred to Phase F

### Schema additions (category.model.ts)
```ts
default_variant_attributes: ObjectId[]    // ref: "attributes"
default_filter_attributes: ObjectId[]     // ref: "attributes"
```

**MOD M1: NO cached resolved field on category doc.** Resolve on-the-fly each call with `visited Set` + 10-level cap. Removes staleness bugs from parent change / attribute delete / category re-parent. Admin form-load only — low traffic, 10 queries max acceptable.

### Behavior rules (all locked)

| Rule | Decision |
|------|----------|
| All depth levels supported (root + sub + sub-sub + infinite) | ✅ |
| Inheritance: empty own defaults → walk parent chain | ✅ |
| Inheritance: own defaults present → **merge with parent** (union, deduplicated) | ✅ (Daraz/Amazon standard) |
| Defaults are SUGGESTIONS — admin can override on product form | ✅ |
| Existing products UNAFFECTED when category defaults change | ✅ |
| Recursion safety: hard cap at 10 levels deep + visited-set cycle break (MOD M1) | ✅ |
| Orphan cleanup: self-healing — skip dead refs at resolve time (MOD M3) | ✅ |
| Merge order: parent-first then own; de-dup by attribute._id, first occurrence wins (MOD M5) | ✅ |

### Admin UX

**Category create/edit form:**
- Two multi-select dropdowns: "Default Variant Attributes" + "Default Filter Attributes"
- Inheritance hint: *"Currently inheriting from parent: [Size, Color]. Add your own to merge."*

**Product form auto-load (MOD M2 — non-destructive):**
- Category change → backend call `GET /category/:id/defaults` (resolved with parent merge)
- **If `product_attributes` is empty:** auto-populate + show banner *"Auto-loaded from category — modify if needed."*
- **If admin already has attributes:** do NOT overwrite. Show banner *"💡 Category defaults available: [Size, Color]. Apply?"* with explicit **Apply** button (merges into existing) and **Dismiss** button.
- **MOD M7: Race-safe** — abort previous in-flight `/defaults` request when category changes again; OR compare requested `categoryId` against latest before applying response.

### Storefront filter sidebar (locked)

**Source:** Hybrid (Option C)
```
sidebar attributes = category.default_filter_attributes (resolved with inheritance)
                   ∪ products' own product_attributes[].show_in_filter (where true)
```

**MOD M5 — De-dup spec:** union by `attribute._id`. If same attribute appears in both sources, count once. Order = category-defaults first (parent-first), then product-driven extras.

**Empty value handling:** Hide (Option A — industry standard)
- Filter sidebar only shows attribute values that at least one product in the current view actually has
- 0-count values hidden, no greyed-out placeholders
- **MOD M4: Single aggregation pipeline** — `$unwind` over products in current view → `$group` by `product_attributes.values._id` → returns `value_id → count` map in ONE query. Prevents N+1 (200 products × 20 values would otherwise be 4000 queries).

### Backend resolution helper
- New service `resolveCategoryDefaults(categoryId)` — walks parent chain on-the-fly, merges, deduplicates
  - Uses `visited Set` to break circular parent loops (MOD M1)
  - 10-level hard cap (belt + suspenders)
  - Filters out dead attribute refs by checking `attribute.findById` returns non-null (MOD M3 — self-healing, no transactional cascade needed on attribute delete)
- New endpoint `GET /category/:id/defaults` — returns resolved arrays
  - **MOD M8: Public (no `verifyToken`)** — used by admin form AND storefront filter; no sensitive data exposed (only attribute name + display_type references).
- **MOD M6 — Storefront optimization:** bake resolved `filter_attributes` into the existing category-page payload (the one `/category/tree` or product-list response already returns). Avoids extra round-trip on every category page load. Admin form continues using the dedicated `/defaults` endpoint.

### Files
Backend: category.model.ts, category.interface.ts, category.controllers.ts, category.services.ts (resolveCategoryDefaults helper + agg pipeline for value counts)
Admin: CategoryPage form (multi-select + inheritance hint), ProductNew/ProductForm category-change effect (non-destructive apply pattern + race-safe abort)
Frontend: productFilter consumer (read baked resolved attributes from category-page payload)

## Phase C — PDP Variation Picker Rewrite (~1.5h)

**Edge-audit 2026-06-01: 10 modifications applied (3 BLOCKERS + 5 HIGH + 2 MEDIUM all addressed). CM2 verified — no backend schema rework needed; switch helper data source from snapshot to populated `product_attributes`.**

### Consumes Phase 0 + A + B output
- Phase 0 ensures `attributes_details[i].attribute_id` is correct (but we WON'T use this snapshot anymore — see CM2)
- Phase A provides display_type per attribute
- Phase B doesn't directly affect PDP picker (filter sidebar only)

### Critical data-source switch (CM2)

PDP backend (`findAProductDetailsServices`) already populates `product_attributes[].attribute_id` with the **full attribute doc**, including source `attribute_values[]` (each with source `_id`). Helper output rebuilt from this — NOT from `attributes_details` snapshot whose `attribute_values[]._id` are Mongoose-autogen subdoc ids that DON'T match `variation.combination[]` ids.

**Consequence:** `attributes_details[]` snapshot becomes display-only legacy field (used elsewhere for spec-table fallback), Phase C ignores it entirely for picker logic.

### Changes

**Helper (`variantAxisAttributes` in helper.js) — REWRITTEN per CM2 / CM1:**
- Input source: `product.product_attributes[]` (populated)
- Filter to variant axes only via `product.variant_axes[].attribute_id` set
- Per axis emit `{ attribute_id, attribute_name, display_type, attribute_values: [...] }` where `attribute_values` = the chosen value docs filtered from the attribute's full value list by the row's `value_ids[]`
- `display_type` injected from `attribute_id.display_type` (CM1 — no backend change)

**Matching logic (`findVariation` in SingleProduct.jsx) — REWRITTEN per CM2:**
- Replace fragile name-slug matching with `combination[]` set intersection
- Build `selectedValueIds: Set<string>` from current selections (sorted is fine — set semantics)
- For each variation: `combination` array converted to Set → equality compare (same size + every element in selected)
- Order-agnostic; works with Bangla/emoji/special chars (no string slug join needed)

**Cart snapshot back-compat (CM3):**
- Keep existing `variation_name` string in cart snapshot (display label for invoices, history, courier slips)
- ADD `combination[]` ID array copy alongside it (used for cart-load re-resolve after variation edit)
- Existing carts unaffected (combination field absent → fall back to variation_name match as today)

**Rendering (driven by attribute.display_type):**
- **Swatch:** rounded circle, hex background, ring border on select, fallback grey when no hex
- **Button:** rounded pill, theme-colored on select
- **Dropdown:** native select with search filter (CM7 — name only, case-insensitive, locale-aware Bangla), scrollable
- All respect 16-desktop / 8-mobile cap → `[+N আরো]` modal beyond
- **CM6 — Pre-computed availability map** built once on mount: `Map<value_id, { hasInStock, anyActive }>` from variations. O(1) per chip lookup.
- **CM9 — Out-of-stock combinations: greyed + clickable** with OOS tooltip/message (not silently disabled — buyer gets feedback)
- **CM10 — `aria-label` on every chip** for screen reader accessibility (value_name, regardless of swatch hex)

**Modal axis selector (`ModalAxisSelector.jsx` — NEW component):**
- **CM8** — implements ESC, click-outside close, body scroll-lock, focus-trap
- Search bar at top (CM7 spec)
- Tap-select closes modal

**Mandatory axes:** All variant_axes treated as mandatory (per edge-audit H3 decision). `is_mandatory` field deprecated (kept in schema for back-compat, ignored in logic).

**Add-to-cart guard:** Disabled until ALL axes have a selection.

**URL state (CM5 — already shipped, clarified):** `?size=m&color=jet-black` parsed into `{ axisAttrId: valueId }` map then resolved via the same combination[] set intersection — NOT a 1:1 mapping with the (sorted) combination array.

**Per-variant gallery auto-switch (CM4):** explicitly **DEFERRED** to Phase F backlog. Phase C does not auto-switch product gallery on swatch select; ensures picker doesn't crash on variation_images[] existence.

### Files
Frontend: SingleProduct.jsx, helper.js, new ModalAxisSelector.jsx component, ProductHighlightSection.jsx (chip render rewrite)

### NO backend changes (CM2 verified)
- `combination[]` already on variation doc, surfaces in PDP response
- `product_attributes[].attribute_id` already populated with full attribute doc including `display_type`
- No snapshot migration, no new field, no new endpoint

## Phase E — Inline Attribute Creation (~1h)

**Edge-audit 2026-06-01: 9 modifications applied (3 BLOCKERS + 4 HIGH + 2 MEDIUM all addressed).**

### Features

**1. "+ Create new attribute" button (in StepOneVariation, next to attribute multi-select)**
- Opens existing `AddAttribute` modal (REUSED, not duplicated) with `onCreated(attribute)` callback
- Save → POST /attribute → modal closes → attribute injected into `selectedAttributes`
- **EM1: Backend POST returns the created doc** (`{ ...sendResponse, data: newAttribute }`) so no name-match race on inject

**2. "+ Add value" button per-selected-attribute panel**
- **EM5: Lives inside each `selectedAttributes[i]` row** in StepOneVariation, NOT inside multi-select dropdown
- Inline mini-form: value name + hex (if attribute.display_type === swatch) + weight (if attribute.tracks_weight)
- **EM4: Fetches fresh attribute before PATCH** to avoid stale-list overwrite, then sends `existing values + new` combined → /attribute PATCH
- **EM8: Frontend duplicate-name pre-check** (case-insensitive trim compare) before POST → save a round-trip
- On success: invalidate `["/api/v1/attribute"]` query → newly added value auto-checked for this product

**3. Form draft auto-save (sessionStorage, NOT localStorage — owner-confirmed)**
- **EM2: Create mode ONLY** — key `fs_product_draft_create`. Update mode never restores or saves draft.
- Debounced 1s save on form field / state changes
- Timestamp stored with each save
- On product create page mount: if draft exists and `updated_at` within 30 min → show toast with **EM7: two-action toast** `[Draft restored]  [Discard]`. Older than 30 min → silently clear.
- On form submit success → clear sessionStorage
- **EM3: Whitelisted serializable fields only:**
  - INCLUDE: `product_name`, `product_slug`, `description` (text), `meta_*`, prices, weights, dimensions, custom fields, `selectedAttributes` (ids only), `axisById`, `showInFilterById`, scalar product_type, tier/group prices
  - EXCLUDE: file previews (object URLs), `inputValueData` (variation rows — rebuilt from attrs on hydrate), large blobs
  - Wrap `setItem` in try/catch with toast on `QuotaExceededError`
- **EM6: Restore filter** — on hydrate, filter selectedAttributes against current `allAttributes` fetch; drop deleted ids; toast "X attributes from your draft are no longer available" if any
- **Why sessionStorage:** auto-clean on tab close, no cross-tab leak, no stale data accumulation

### UX
- **EM9: Responsive modal** — `items-end sm:items-center` so mobile shows bottom-sheet, desktop centered. (Polish v1; full bottom-sheet animations deferred to F.)
- ESC + click-outside close (confirm if unsaved values in mini-form / create-modal — simple `confirm()` for v1)
- Loading spinner during save
- Toast on success → auto-select in form

### Edge cases
| Case | Handle |
|------|--------|
| Network fail during save | Modal stays open, retry, data preserved |
| Duplicate attribute name | Backend reject, toast "এই attribute already exists" |
| Concurrent admin creating same name | Backend unique constraint → friendly error |
| Modal create success but parent product save fail | Attribute persists (no rollback); admin retries product save |
| Draft has attribute deleted since save | EM6 — filter + toast skipped list |
| sessionStorage quota exceeded | EM3 — try/catch + toast "Draft save failed (storage full)" |

### Files
- Admin: `AddAttribute.jsx` (add `onCreated` callback prop + small backend response tweak), `StepOneVariation.jsx` ("+ Create" button + "+ Value" per-row + AddValueInline component), `ProductForm.jsx` (draft save/restore wiring)
- Backend: `attribute.controllers.ts` (postAttribute returns created doc in `data` field — 1-line tweak)
